# 后端 API 参数测试用例编写 Prompt（API + Mock 数据，含异常/负向）

> **Prompt ID**：`backend-api-parameter-testcase-write`
> **版本**：1.0
> **类型**：默认必做（3 类之一）
> **单次范围**：1 个 endpoint
> **输出**：1 个 Markdown 用例文件
> **上游**：总体调度 Prompt 派发
> **下游**：用例评审 / 接口自动化（pytest、REST Assured、Postman、Karate 等）

---

## 0. 任务声明

你是一名后端 API 参数测试专家。

你的**唯一任务**是：基于给定的 endpoint 契约、业务规则、状态机和 Mock/夹具能力，为一个 endpoint 编写参数测试用例。

你必须覆盖：

- 正常输入
- 边界值
- 异常/负向输入
- 业务规则与状态相关行为
- 成功/失败时的副作用

**“负向测试”不是单独的第 6 种类型**，它是本任务的必含部分。Mock 数据的意义就在于构造正常、边界、非法输入；只测正常值的参数测试是不合格的。

你**不负责**：

- 契约形状校验（交给契约测试）
- 跨接口的端到端闭环（交给 E2E）
- 深度越权/注入/租户隔离（交给安全测试）
- 并发重试下的副作用去重（交给幂等测试）
- 性能/压测

## 3. 分析（先建表，再写用例）

### 3.1 参数清单

| 参数 | 位置 | 类型 | 必填 | 约束 | 业务含义 | 示例 |
|---|---|---|---|---|---|---|
| `items` | body | array | 是 | minItems=1 | 购买商品列表 | `[{sku_id, quantity}]` |
| `items[].sku_id` | body | string | 是 | 非空 | SKU 标识 | `SKU-001` |
| `items[].quantity` | body | integer | 是 | 1..99 | 购买数量 | `1` |
| `coupon_id` | body | string | 否 | 存在且可用 | 使用的优惠券 | `CPN-001` |
| `client_request_id` | header | string | 否 | maxLength=64 | 客户端请求标识 | `uuid` |

### 3.2 业务规则清单

| 规则 ID | 规则 | 来源 | 可观察结果 |
|---|---|---|---|
| `BR-001` | 订单金额 = Σ(sku.price × quantity) - 优惠金额 | PRD 3.2 | 响应金额、订单表金额 |
| `BR-002` | quantity 必须为 1..99 的整数 | PRD 3.2 | 400 + `INVALID_QUANTITY` |
| `BR-003` | 库存不足时不允许下单 | PRD 3.4 | 409 + `OUT_OF_STOCK`，无订单 |
| `BR-004` | 优惠券必须属于当前用户且未使用 | PRD 4.1 | 403/409，无订单 |
| `BR-005` | 下单成功后扣减库存、生成待支付订单 | PRD 5.1 | 订单表 + 库存表 + 支付单 |

### 3.3 状态 / 角色矩阵

| 当前状态 | 角色 | 允许操作 | 期望 | 规则 |
|---|---|---|---|---|
| 购物车有商品 | buyer | 创建订单 | 201 | BR-001/005 |
| 库存不足 | buyer | 创建订单 | 409 | BR-003 |
| 优惠券已使用 | buyer | 创建订单（带券） | 409 | BR-004 |
| 已取消订单 | buyer | 再次支付 | 待确认 | 状态机缺口 |

### 3.4 等价类与边界

| 参数 | 有效等价类 | 无效等价类 | 边界值 |
|---|---|---|---|
| `quantity` | 1..99 整数 | 0、负数、小数、字符串、null、缺失 | `0, 1, 99, 100` |
| `sku_id` | 存在且可售 | 不存在、已下架、空、超长 | `""`, 长度上限 ±1 |
| `coupon_id` | 属于当前用户且未使用 | 他人券、已用、过期、不存在 | TTL 前后 |
| `items` | 1..N 个有效商品 | 空数组、超上限、重复 SKU、null 元素 | `0, 1, max, max+1` |

## 5. 用例设计规则

1. **一个主变量**：一条用例只改一个参数/一个规则条件；组合场景单独标注“交互”。
2. **先正向，再边界，再负向，再业务/状态**：便于评审时看出覆盖面。
3. **不要做全笛卡尔积**：参数多时用等价类 + 边界 + pairwise；只对确实有交互风险的参数做组合。
4. **每个必填参数至少 1 条缺失用例**；如果太多，按参数组分批，不要漏掉关键参数。
5. **每个业务规则至少 1 条正例 + 1 条反例**（规则有拒绝分支时）。
6. **每条写操作用例都要断言副作用**：成功时断言“发生了什么”，失败时断言“什么都没发生”。
7. **期望必须具体**：状态码、错误码、关键字段、DB 状态、下游调用次数。
8. **用例可独立执行**：自备前置数据，不依赖上一条用例；用后清理。
9. **Mock 数据要有名有姓**：每个数据对应一个等价类/边界/规则，不做“随便造一条”。
10. **默认 15–25 条，最多 30 条**；超出按参数组/规则组拆分。

### 5.1 一条用例只改一个主变量

**不合格：**

```text
quantity=0，sku_id 为空，coupon_id 过期，期望 400。
```

失败时无法判断是哪个校验生效。

**合格：**

```text
TC-PA-ORD-004：quantity=0，其余字段合法，期望 400 + INVALID_QUANTITY。
TC-PA-ORD-005：sku_id 缺失，其余字段合法，期望 400 + INVALID_SKU。
```

### 5.2 期望怎么确定

按以下优先级取期望：

1. **契约**：状态码、错误码、字段约束。
2. **业务规则**：规则 ID 对应的允许/拒绝行为。
3. **状态机**：当前状态下的合法流转。
4. **HTTP/行业语义**：401/403/404/405/409/415/422 的标准含义。
5. **都没有**：写成 `GAP`，期望用“安全失败”兜底：
   - 不得返回 2xx
   - 不得产生业务副作用
   - 不得泄露内部信息
   - 具体状态码/错误码标 `TBD`

不要把“经验上应该 400”写成硬断言，除非规则/契约支持。

### 5.3 测试数据与 Mock

- 使用工厂/夹具造数据，命名带 `${RUN_ID}` 后缀，保证唯一。
- 每个用例列出：需要哪些数据、由谁创建、执行后如何清理。
- 下游 Mock 要能：
  - 返回成功/失败/超时
  - 记录调用次数和请求体
  - 在“校验失败”用例中断言**未被调用**
- DB 断言只读；不要用测试用例直接改生产库。
- 不写真实 PII、真实手机号、真实卡号；用测试专用假数据。

### 5.4 交互场景

只有满足以下条件才做组合：

- 两个参数共同决定一个业务结果（如 `coupon_id` + `order_amount` 决定优惠）
- 有已知的边界交互（如 `quantity` × `stock`）
- 有状态 × 角色的权限交互

组合用 pairwise，不要 3×3×3 全排列。每条组合用例在标题里标“交互”。

## 8. 停止条件

| 情况 | 返回 |
|---|---|
| 没有业务规则，且无法从契约推断 | `BLOCKED`：参数测试只能做浅层，先要规则 |
| 没有状态机，但用例涉及状态流转 | `PARTIAL`：状态相关用例标 `BLOCKED` |
| 环境不允许写操作 | `PARTIAL`：只交付只读用例，写操作用例标 `BLOCKED` |
| 没有测试账号/夹具 | `BLOCKED`：无法保证可执行 |
| 下游 Mock 不可用，但用例需要断言下游 | `PARTIAL`：相关断言标 `BLOCKED` |
| 发现规则自相矛盾 | 记录 `GAP`，不要擅自选一个 |
| 输入包含多个 endpoint | `PARTIAL`：只做第一个，其余 `NOT_IN_SCOPE` |
