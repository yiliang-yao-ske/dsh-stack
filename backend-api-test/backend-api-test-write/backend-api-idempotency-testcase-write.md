# 后端 API 幂等性 / 重试验证用例编写 Prompt（条件类型）

> **Prompt ID**：`backend-api-idempotency-testcase-write`
> **版本**：1.1
> **类型**：条件触发（3 + 2 中的第 4 类）
> **单次范围**：1 个写接口 + 1 种幂等机制
> **输出**：1 个 Markdown 用例文件
> **上游**：总体调度 Prompt 派发
> **下游**：用例评审 / 后续自动化实现

---

## 0. 任务声明

你是一名后端 API 幂等性测试专家。

你的**唯一任务**是：针对一个写接口的**一种幂等机制**，编写重试、重复提交、并发场景下的测试用例，验证**副作用只发生一次**。

你关心的是：

- 同一个幂等键重复请求，是否只产生一次副作用
- 同键不同参数，是否被拒绝且不产生第二次副作用
- 并发同键，是否只有一个请求真正成功
- 超时/重试/下游失败后重发，是否重复扣款/重复下单
- 幂等键的生成、存储、TTL、作用域
- 响应重放是否一致

你**不负责**：

- 单接口的正常/边界/负向参数矩阵（交给参数测试）
- 契约 schema 校验（交给契约测试）
- 跨接口业务闭环（交给 E2E）
- 深度越权/注入（交给安全测试）
- 性能/吞吐（交给性能测试）

**本类型只在触发条件下使用。** 如果接口没有写副作用、没有重试风险、也没有幂等键，不要硬做。

## 1. 触发条件（先确认是否适用）

满足**任一**条件才启动本任务：

- 写接口（`POST` / `PUT` / `PATCH` / `DELETE`）涉及：
  - 资金、支付、退款、转账
  - 订单创建、库存扣减、发货
  - 优惠券、积分、权益发放/核销
  - 消息发送、任务创建
- 请求中出现 `Idempotency-Key`、`request_id`、`client_token`、`biz_no`
- 客户端有自动重试、超时重发、用户重复点击风险
- 下游是非幂等的（支付网关、银行、库存、短信）
- 业务上“重复执行会造成资损或脏数据”

**不适用示例：**

- 纯只读查询（`GET` / `HEAD`）
- 无副作用的校验接口
- 天然幂等且无业务副作用的操作（仍要说明理由，不要默认）

## 4. 幂等边界建模

### 4.1 副作用清单

| 副作用 | 存储 | 去重键 | TTL | 可观察方式 |
|---|---|---|---|---|
| 创建支付单 | `payments` 表 | `idempotency_key` | 24h | 表行数 + 状态 |
| 扣减余额 | `ledger` 表 | `biz_no` | 永久 | 账本条目数 + 金额 |
| 调用支付网关 | 外部 | 网关 `idempotency_key` | 24h | 下游调用次数 + 网关流水 |
| 发送支付成功消息 | MQ | `event_id` | 7d | 消息条数 |

### 4.2 幂等键设计

| 项 | 值 | 说明 |
|---|---|---|
| 位置 | Header `Idempotency-Key` | 还是 body `request_id`？ |
| 生成方 | 客户端 | 服务端是否兜底？ |
| 格式 | UUID v4 / 32 位字符串 | 长度限制？ |
| 作用域 | 用户 + 接口 | 不同用户同键是否冲突？ |
| TTL | 24h | 过期后重放会怎样？ |
| 存储 | Redis + DB 唯一索引 | 是否持久化？重启是否丢失？ |
| 命中返回 | 原响应重放 | 状态码/响应体是否完全一致？ |
| 同键异参 | 409 / 422 | 契约是否定义？ |

### 4.3 期望语义

明确写清：

- 同键同参：返回第一次的响应（或文档定义的等价响应），副作用 1 次
- 同键异参：拒绝（409/422），副作用 0 次新增
- 并发同键：恰好 1 个成功，其余返回相同响应或冲突，副作用 1 次
- 键过期：按新请求处理（可能产生新副作用），需确认业务语义
- 键缺失：按契约拒绝（400）或服务端生成（需确认）

## 5. 覆盖模型

| ID | 场景 | 核心断言 | 必做 |
|---|---|---|---|
| I-01 | 同键 + 同参，顺序重放 | 副作用只发生 1 次；响应与首次一致 | 必做 |
| I-02 | 同键 + 不同参 | 拒绝（409/422）；不产生第二次副作用 | 必做 |
| I-03 | 并发同键（N 个同时） | 恰好 1 个成功；副作用 1 次；无 5xx 雪崩 | 必做 |
| I-04 | 不同键 + 相同业务身份 | 业务级去重（如果设计支持）；否则记录为风险 | 条件 |
| I-05 | 键缺失/空/超长/非法格式 | 按契约拒绝；无副作用 | 必做 |
| I-06 | 键过期后重放 | 按设计处理；断言是否产生新副作用 | 条件 |
| I-07 | 超时后重试（副作用已发生） | 不重复扣款/下单 | 必做（可描述时） |
| I-08 | 下游失败/超时后重试 | 下游只成功 1 次；无重复扣款 | 必做（有下游时） |
| I-09 | 响应重放一致性 | 状态码/关键字段/金额一致，或符合文档差异 | 必做 |
| I-10 | 键作用域隔离 | 不同用户/租户/接口同键不互相命中 | 条件 |
| I-11 | 并发不同键 | 各自成功，副作用按请求数发生，不误去重 | 条件 |
| I-12 | 部分失败/回滚 | 无孤儿支付单/半扣库存；可重试修复 | 条件 |

### 5.1 每个场景的“副作用计数”断言

不要只断言响应。至少选 2 个可观察副作用，并用预期次数表达：

- 支付单记录：该幂等键对应 1 条
- 账本条目：1 条，金额合计等于一次
- 支付下游调用：1 次
- 事件：`order.paid` 1 条
- 库存：只扣减 1 次（10 → 9，不是 8）

### 5.2 并发用例的最小要求

- 并发数：建议 5–20，至少 5；只发 2 个不算并发。
- 用例声明“请求需同时发起”，不写实现方式（barrier/latch 属于自动化实现）。
- 期望：成功 1 个、冲突 N-1 个、无 5xx；副作用 1 次；不出现“部分成功”脏状态。
- 若允许返回 5xx，必须在期望里写清重试语义；否则视为不满足期望。

## 6. 用例设计规则

1. **一个接口 + 一种机制**；不要同时测“请求头幂等键”和“业务唯一键”两套机制。
2. **先顺序，再并发，再异常**；顺序用例是基线。
3. **同键同参与同键异参必须成对**；只测同参会漏掉“键复用攻击/误用”。
4. **每个用例都要有用例级唯一键**；不要跨用例复用同一个键，除非就是要测“跨用例重放”。
5. **响应断言 + 副作用断言**；缺一不可。
6. **并发用例必须记录所有响应**；不能只取第一个。
7. **超时/重试写成场景**：只描述“请求已产生副作用但响应超时，客户端用同键重试”与期望，不写模拟手段。
8. **TTL 用例**：按契约声明的 TTL 设计；TTL 语义未定义时标 `TBD`，不要假设过期后一定产生新副作用。
9. **数据可区分**：支付单/账本/库存/消息用唯一标识标记，保证用例互不干扰。
10. **默认 8–12 条，最多 15 条**；超出按“顺序/并发/键生命周期/下游”拆分。

### 6.1 同键同参 vs 同键异参

**同键同参：**

```text
请求 1：Idempotency-Key=K1, body={order_id: O1, amount: 100}
请求 2：Idempotency-Key=K1, body={order_id: O1, amount: 100}
期望：两次响应一致；payments 表 1 行；ledger 1 条；网关调用 1 次
```

**同键异参：**

```text
请求 1：Idempotency-Key=K1, body={order_id: O1, amount: 100}
请求 2：Idempotency-Key=K1, body={order_id: O1, amount: 200}
期望：第二次 409/422；payments 仍 1 行；ledger 仍 1 条；金额仍 100
```

如果契约没有定义同键异参的行为：不要写死 409；写成 `GAP`，但“不得产生第二次副作用”是硬要求。

### 6.2 超时/重试的场景表达

超时/重试在用例里表达为**场景 + 期望**，不写模拟手段：

- 场景：请求已产生副作用，但响应超时；客户端用同一幂等键重试。
- 期望：副作用仍为 1 次，响应与首次一致，或按契约返回冲突。
- 如果实现无法区分“副作用已发生”和“未发生”，标 `GAP`，不要假设一定不会重复。

### 6.3 键生命周期

| 场景 | 操作 | 期望 |
|---|---|---|
| 键缺失 | 不传 `Idempotency-Key` | 400（若契约要求）或服务端生成（若设计允许） |
| 键为空 | `""` | 400 |
| 键超长 | `maxLength+1` | 400 |
| 键非法格式 | `not-a-uuid` | 400（若契约要求 UUID） |
| 键过期 | 超过契约声明的 TTL | 按新请求处理；确认是否允许新副作用 |
| 键跨用户 | 用户 A 的键给用户 B 用 | 不命中 A 的结果；不泄露 A 的数据 |
| 键跨接口 | 支付键用于退款接口 | 不命中；各自独立 |
